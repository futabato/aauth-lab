## 1. OAuthによるアプリケーションへの権限の委譲

**結論**：OAuthと拡張は、本人の資格情報を第三者へ渡さずに権限を委譲し、その範囲と使用する鍵を制御する手段を提供する。

**導入とのつながり**：導入で挙げたアクセス権限の委譲と操作ごとの確認を、既存の認可基盤でどう構成できるか確かめ、AAuthとの比較の前提にする。

### パスワード共有とアクセス権の委譲

RFC 6749 §1の原文で、認可の層とクライアント・リソース所有者の役割分離を確認する。パスワードを第三者へ渡す方式の課題から、リソース所有者・クライアント・認可サーバー・リソースサーバーの分担へ進む。APIをサービスへ操作を要求する仕組みとして初めて説明する。認証と認可を区別し、エージェントもAPIを使うクライアントとしてこの基盤を使えることを示す。

### 追加同意と操作の制限

RFC 9396 Abstractの原文を引き、`authorization_details`で細かな認可条件を伝える拡張だと説明する。追加同意、再認証、操作直前の確認をアプリケーションの方針として整理する。RARが詳細な要求を表せることと、API側で対象・操作の意味を定義して強制する必要があることを併記する。通常の削除scopeは「文書Aを一度だけ削除する許可」ではない。

### トークンと鍵の結び付け

RFC 9449 §3の原文でクライアント認証との区別を示す。DPoPによる鍵の所持証明を説明し、クライアント認証そのものとは区別する。OAuthと拡張が機能を提供していても、実際のシステムでは登録管理・追加確認・トークン保管をどこが担うかを決める必要があるとして第2節へつなぐ。

**根拠**：[RFC 6749 §1](https://www.rfc-editor.org/rfc/rfc6749#section-1)、[RAR / RFC 9396](https://www.rfc-editor.org/rfc/rfc9396)、[DPoP / RFC 9449](https://www.rfc-editor.org/rfc/rfc9449)。利用例は原稿のGoogle・Microsoft公式資料を参照する。

## 2. HellōのMCPサーバー開発で表面化した認可の課題

**結論**：HellōのMCPサーバー開発では、登録の運用、削除の確認、トークンの保管について、既存基盤をどう使うかの実装判断が必要になった。

**前節とのつながり**：OAuthの機能を組み込む際の実装判断を、既存の管理APIをMCPツールとして提供したHellōの事例で具体化する。その前に、MCPが連携方式の共通化を目指して公開された背景を短く説明し、登録・削除の確認・トークン保管の配置を読む目的へつなぐ。

MCPの背景説明は第2節冒頭の3段落以内に収める。Anthropicが2024年11月25日の公開記事で挙げた、モデルの性能が向上しても業務データや既存システムとの接続に個別の実装が必要になるという問題設定を示す。接続先ごとの専用実装で連携先を増やしにくいことを述べた16語の原文を、公開日と出典付きで引用し、共通の連携方式を使って負担を減らす狙いを日本語で説明する。MCP以前は外部データを利用できなかった、各データソース向けの実装がすべて不要になった、とは書かない。[AnthropicのMCP公開記事（2024年11月25日）](https://www.anthropic.com/news/model-context-protocol)

連携方式の共通化と、本人からのアクセス許可や操作権限の判断は別の設計課題としてつなぐ。2024年の公開背景と、本記事で扱う2025-06-18版のHTTP認可仕様を区別し、Hellōの保護された管理APIの事例へ進む。認可の問題がMCPによって新たに生まれたとは扱わず、冒頭のCodexとGoogle Driveの連携がMCP経由かも推測しない。

### Hellō管理APIへの接続

MCPを、AIアシスタントなどのアプリケーションを外部のデータやツールへ接続するプロトコルとして説明する。続いてHellōを認証サービスとして紹介し、管理対象のHellōアプリの登録と、管理APIを呼ぶMCPクライアントのOAuth登録を分ける。本人のログイン・同意もDCRとは別の処理であることを説明する。

**図1：ツール呼び出しの経路（2矢印）**。登録とアクセストークン取得を済ませた後の **MCPクライアント → MCPサーバー → Hellō管理API** だけを描く。最初の矢印は「アクセストークン提示・ツール呼び出し」とする。Hardtの実測通信記録として扱わず、アクセストークンの形式や管理APIへ渡す資格情報は特定しない。

### クライアント登録の運用

共通の`client_id`と任意の`redirect_uri`はHardtの実装選択として扱う。MCP 2025-06-18 AuthorizationのOverviewのSHOULDを原文で示し、認可自体は任意でHTTP認可の仕様として読む条件と、非対応ASの代替を説明する。MCPの2025-06-18版ではDCRはSHOULDで代替があり、RFC 7591にも登録管理の選択肢がある。無制限の永続登録が必須とは書かない。

### 削除の確認

Web UIの`DELETE`入力による確認と、`mcp` scopeから削除を除外した判断を分ける。当時のElicitationにも確認機構があったことを示し、Hellōが採用しなかった理由とクライアント対応は未確認とする。

### トークンの保管

refresh tokenをアクセストークンの再取得に使うものと説明し、発行しない方針を漏えいへの懸念に基づく選択として扱う。漏えい事故の報告とはしない。接続先が増えると、接続先ごとの認可処理とトークンを管理する仕事がクライアントに残ることを示す。実装記事のLessons Learnedから本人の見解を示す短文を引用し、仕様上の結論と区別する。OAuth拡張の可能性と既存APIへの利用にも触れて、第3節の移管提案へ進む。

**根拠**：[Hellō Admin MCP Server](https://www.hello.dev/docs/admin-mcp/)、[Hardtの実装記事](https://blog.hello.coop/posts/say-hello-to-ai)、[MCP 2025-06-18の概要](https://modelcontextprotocol.io/specification/2025-06-18)、[MCP 2025-06-18 Authorization](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization)、[Elicitation](https://modelcontextprotocol.io/specification/2025-06-18/client/elicitation)、[DCR / RFC 7591](https://www.rfc-editor.org/rfc/rfc7591)。Hellōの背景説明は原稿の公式資料を参照する。

## 3. MCPの認可に関する提案からAAuthに至る経緯

**結論**：SEP 1299とAAuthには認可処理の配置を変える関心が共通するが、同じ構成・採否手続きの提案ではない。

**前節とのつながり**：クライアントに残った仕事をサーバー側へ移す案と、その移管で増える責任を読む。

### 認可処理のサーバー側への移管

discovery・OAuthフロー・トークン保管の移管、インスタンスの鍵とHTTP署名、利用者への直接の対話を説明する。背後の既存APIとのOAuthは維持できる一方、サーバー侵害時に複数利用者へ影響することも扱う。2025-09-02のSEP閉鎖コメントを示し、「提案のその部分」と提案全体の採用を区別する。SEP 1415全体の採用状況は未確認。

### 独立したプロトコルの提案

2026-04-02の初稿公開と、2026-09-25のprotocol-11を歴史上の節目として分ける。AAuthでは本人を代表するPSを役割として取り出すことを示し、第4節の役割一覧と通信の説明へつなぐ。初稿公開を構想の誕生日とせず、SEPがそのままAAuthの標準化になったとは書かない。

**根拠**：[SEP 1299](https://github.com/modelcontextprotocol/modelcontextprotocol/issues/1299)、[閉鎖理由のコメント](https://github.com/modelcontextprotocol/modelcontextprotocol/issues/1299#issuecomment-3244750018)、[SEP 1415](https://github.com/modelcontextprotocol/modelcontextprotocol/issues/1415)、[初稿 -00](https://datatracker.ietf.org/doc/html/draft-hardt-aauth-protocol-00)、[protocol-11](https://datatracker.ietf.org/doc/html/draft-hardt-oauth-aauth-protocol-11)。閉鎖コメントは2026-10-10に照合し、その後の採用状況は未確認。

## 4. AAuthの登場主体と各主体が担う認可処理

**結論**：AAuthはAgentの識別、本人側の許可、リソース側の発行判断と実行時の検査を役割へ配置し、署名付き要求とトークンで結び付ける。

**前節とのつながり**：処理を移すという関心を、誰が判断し、誰が実行を止めるかという具体的な分担へ落とす。

### 登場主体

本人側の判断とAPI側の検査をどう結び付けるかを読むため、要求の図より先に次の6役を一覧で示す。

| 呼称 | 説明する役割 |
|---|---|
| 本人：User（仕様上はPerson） | Agentが代理する人または組織。同意・監督を行う本人とPSを分ける |
| エージェント：Agent | 操作を選び、署名付き要求を送る |
| エージェント提供者：Agent Provider（AP） | Agentの識別子と公開鍵を結び付けるagent tokenを発行する |
| 本人側サーバー：Person Server（PS） | 本人側の判断とperson tokenの発行を担い、モードに応じてauth tokenを発行または仲介する |
| アクセスサーバー：Access Server（AS） | リソース側のポリシーを評価してauth tokenを発行する |
| リソース：Resource | トークン・署名と業務ポリシーを検査し、操作の実行を判断する |

役割と独立サーバーの台数を同一視しない。二者・三者・四者は主要なプロトコル参加者を数え、通常APと本人を含めない。PSによる三者構成を中心に説明し、ASを含む四者構成を後から示す。五つのモードと初回同意の条件は補足へ回す。

### 本人側の許可とAPI側の検査

冒頭の資料整理を、読み取り・移動・削除をAPIで行える架空の文書管理サービスで具体化する。読むことと分類することは最初から許し、移動や削除には追加の許可を求める方針は、説明のための設定でありAAuth仕様の一般要件ではないと示す。PSのSupervisorによる判断とResourceの実行時検査を分ける。所有者チェックと保護文書チェックも別のResourceポリシーとして説明する。許可の取得とAPIの検査を観測するために、架空の文書APIを使うラボへ移る目的を示す。段階的に検証するため、まず通常の`docs.delete`への追加同意と実行時の検査を扱い、文書ID・回数の制約を扱う後続検証と区別する。

### 追加許可の取得

resource tokenによる要求とauth tokenによる許可を区別する。Resourceの要求とAgentのjustificationも混ぜず、PSが本人またはSupervisorの判断を経る流れを示す。

**図2：三者構成での追加許可と再送（6矢印）**。この例のHTTP 401が削除に必要な権限の不足を示す応答であると説明し、追加許可を取得して再送する成功経路を描く。設計図であり、実測結果ではない。

1. Agent → Resource：削除要求（`docs.read`のauth token）
2. Resource → Agent：401とresource token
3. Agent → PS：認可要求（resource tokenなど）
4. PS → Agent：承認後のauth token（`docs.delete`）
5. Agent → Resource：auth tokenで削除要求を再送
6. Resource → Agent：処理結果

本人への追加確認とResourceの検査は注記に置く。本人との対話、PSのpending URLへのpoll、署名検証の細部を省略する。202での保留は第6節「承認待ち・再試行・失効」で区別する。ラボの同意画面は本人認証がなくAgentも自己承認できるため、本人の判断を保護した実証にはしない。

### トークンと署名による検証

agent tokenによるAgentと鍵の結び付け、person tokenによる本人との結び付け、auth tokenによる許可を分ける。JWT発行元の署名とHTTP要求の署名を区別し、期限・audience・scope・対象ポリシーの検査を独立した条件として示す。Resourceが常にAgentの識別子を受け取るとはしない。

### Missionと本人の意図

MissionはPSが判断する仕事の文脈として説明する。`approved_tools`や自然言語の目的は、対象・回数・ローカルツール実行を自動で強制するものではない。正しく署名された要求でも本人の意図から外れ得るため、プロンプトインジェクション防止を保証しない。

### リソース側の認可と四者構成

本人側のPSとリソース側のASによる発行判断を分け、実行時の強制はResourceに残ることを示す。

**図3：四者構成でのauth token取得（7矢印）**。

1. Agent → Resource：認可要求（person token）
2. Resource → Agent：resource token（宛先はAS）
3. Agent → PS：認可要求（resource tokenなど）
4. PS → AS：トークン要求（resource tokenなど）
5. AS → PS：Resource向けauth token
6. PS → Agent：auth tokenを中継
7. Agent → Resource：auth tokenでAPI要求

ASのtoken endpointを呼ぶのはPSとする。初回紐付け・同意、APからのagent token取得、メタデータ取得、署名検証、承認待ちは省略する。この図は発行経路に限定し、APIの応答や副作用まで描かない。分担で減る負担と増える信頼・運用の責任を第5節の比較へつなぐ。

**根拠**：固定仕様の§4.2–4.4、§5–9、§11.3、§11.5。同意表示は§7.4、四者構成の取得経路は§4.2.5・§9.3。詳細な参照リンクは原稿に置く。

## 5. AAuthはOAuthの拡張か、新しいプロトコルか

**結論**：議論の争点は、必要な機能をOAuthの拡張で構成するか、Agentの鍵と本人側の判断を中心に別の基礎から定めるかであり、優位性や採用方針は確定していない。

**前節とのつながり**：役割の配置を理解した上で、同じ要件を満たす既存構成との違いを比較する。

この節は小節を増やさず、著者の設計理由、会合での提案、比較条件、議論の状態の順に読む。Hardtの付録C.4.5からAgentのモデルを出発点とする設計方針を原文引用し、OAuthに変更を重ねると後方互換性を失うという判断を日本語で補う。同付録が述べるOAuth・OIDCとの補完関係も説明する。著者の主張をOAuth全般の不可能性やWG合意へ置き換えず、Aaron PareckiのOAuth拡張案、併用案などを公開記録に基づいて示す。DPoP・RAR・Token Exchangeを正当に扱う。

比較条件は、インスタンス識別、本人側とリソース側の方針、非同期承認、資格情報の保管、既存APIへの接続にそろえる。実装量・信頼先・障害時・移行の負担を評価する必要があるとして第6節へ進む。追加同意の動作デモだけでAAuthの優位性や運用の単純さを証明しない。

**根拠と留保**：[protocol-11付録C.4.5](https://datatracker.ietf.org/doc/html/draft-hardt-oauth-aauth-protocol-11#appendix-C.4.5)、2026-10-05 interimの[公開ノート](https://notes.ietf.org/notes-ietf-interim-2026-oauth-06-oauth)と[チャットログ](https://datatracker.ietf.org/doc/chatlog-interim-2026-oauth-06-202610051300/)、[Token Exchange / RFC 8693](https://www.rfc-editor.org/rfc/rfc8693)。会合資料は2026-10-10に部分照合した。公開ノートを正式議事録・採用決定とせず、その後の最新状態は未確認とする。

## 6. AAuthで解決できること・残る課題と、本記事での検証計画

**結論**：採用する配置の評価には、信頼・待機・停止・操作制約を実装と運用で確かめ、観測できた結果と残る条件を分ける必要がある。

**前節とのつながり**：信頼先や障害時の振る舞いを共通条件で比較するため、トークンの発行前後も確かめる。発行された権限の受け入れ条件、承認待ちの処理、取り消し後の停止を整理し、比較の前提とラボの観測対象を決める。対象・回数の限定条件は通常のscopeと分ける。

### 信頼先と鍵の運用

署名を検証できることと発行元を受け入れることを分ける。§9.3.1のPS–AS信頼確立手順を示した上で、AP・PSの受け入れ方針、鍵の生成・保管・更新、侵害・利用不能の影響を整理する。

### 承認待ち・再試行・失効

401による再送と202によるResource側の保留を説明し、許可の取得と操作の再開を分ける。承認待ちの期限切れと処理完了後の応答消失、再認可・保留終了・結果取得・二重実行抑止を区別する。deferredの再pollとトークン全体の一回限り制御も分ける。失効対応がSHOULDであること、未対応・未到達時に`exp`まで受理され得ることを説明する。

### 操作単位の許可

`docs.delete`と対象・回数の制約、署名後の改ざんと別対象への新しい正しい署名を区別する。R3は探索的な別仕様として扱い、詳細・対象版・成熟度・強制範囲は未確認とする。

ラボでは、読み取り権限で削除できないこと、pending・拒否・削除を含まない権限縮小で副作用がないこと、承認後に適切な権限で削除できることを観測する。HTTP応答だけでなく削除の実行記録とリソースの前後差分で判定し、実験結果は未実測のまま残す。

### 補足：ラボの検証条件と未実施事項

固定スクリプトのAgent・PS・架空の文書APIによる三者フローと、テスト用APを記載する。bootstrap・初回紐付け・初回承認の代替前提、本人認証のない同意画面、protocol-11未準拠、ラボ独自のJWT・HTTP署名処理を限定事項として保持する。独立AS・LLM・多段呼び出しは初期範囲外。

別鍵、期限切れ、別audience、無効なJWT署名、HTTP改ざんを個別の陰性試験にする。通信順序・公開claims・鍵thumbprint・同意遷移・判断主体と理由・データ差分を対応付ける。秘密鍵や本物の認証情報は記録せず、実データ・実アカウントは使わない。信頼できるライブラリを使う方針と未完了部分を区別する。起動・テスト未実施を明記する。

### 補足：署名対象

HTTP署名の基本対象と追加対象、本文・クエリの保護範囲、DPoPとの比較条件を示す。RFC 9449 §11.7の原文で本文・ヘッダーの完全性をDPoP単独では保証しないことを示し、method・URIの保護とTLSへの依存を説明する。改ざん試験では変えた項目が署名対象だったかを記録する。

### 補足：五つのアクセスモードと初回の同意

五つのモードを表で整理する。person tokenはscope・アカウント権限を表すものではないが、識別によるアクセスにつながる場合もある。§13.8・§13.14の本人との結び付けと初回承認の条件を示し、テストで代替した前提を明示する。

### 補足：GNAPとの関係

GNAPを別の再設計の試みとして比較し、OAuth→GNAP→AAuthという必然的な進化にはしない。
