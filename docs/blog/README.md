## 執筆方針

- 硬派な技術記事として、誰が何を登録し、どの権限を判断し、どこで実行を止めるかを具体的に書きます。
- 記事上の決定、一次資料で確認した事実、著者・議論参加者の主張、未確認事項を分けます。確認日と対象版を併記し、過去の調査をそのまま現在の状態として扱いません。
- OAuth と拡張でも追加同意や DPoP は可能です。動作デモだけで AAuth の優位性を証明したとは書きません。唯一の解・標準化完了・プロンプトインジェクション防止の保証としても扱いません。
- `docs.delete` への同意、特定の文書 ID への同意、一度限りの実行は別の制約です。別対象への新しい正しい署名付き要求が通ることを、直ちにプロトコルの脆弱性とは扱いません。対象・回数の制御は Resource のアプリケーションポリシーや探索的 R3 と分けます。
- 未実測の実験を成功例や失敗例に変えません。記録する条件・証跡はルート README に従い、秘密鍵・本物の認証情報・実データを文書やリポジトリに入れません。
